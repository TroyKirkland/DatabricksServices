L100What it is

Hosted web apps inside Databricks. Bring Python or Node (Streamlit/Dash/Flask/FastAPI/Gradio/Reflex/React); declare resources in app.yaml; deploy. Workspace OAuth + UC + serving + Lakebase access + HTTPS URL.

  • Hosted: no clusters/K8s.
  • UC-integrated: app identity has fine-grained access.
  • Multi-framework: Python web + Node.

L200The product surface

  • app.yaml: command + env + resources + scopes.
  • Runtimes: Streamlit, Dash, Gradio, Flask, FastAPI, Reflex (Python); React, Angular, Svelte, Express, FastAPI+React via APX (Node).
  • Resources: UC tables/volumes/connections, serving endpoints, Lakebase, secrets, SQL warehouses, Genie Agents, MLflow experiments, AI Search indexes, UDFs, other apps (app-to-app).
  • App telemetry: traces, logs, and metrics written to Unity Catalog tables.
  • Auth: app identity (SP) + OBO (act-as-user).
  • HTTPS endpoint with workspace SSO; can be embedded in external sites.
  • Logs + observability in UI.
  • Deploy via CLI / DABs / UI.

L300Architecture

[Browser] → HTTPS + OAuth → [App endpoint] → [Container running your framework]
                                                  ├ env from app.yaml resources
                                                  ├ App identity → UC / endpoints / Lakebase
                                                  └ Optional OBO → user identity

Resources translate to env vars (e.g., MY_ENDPOINT_URL, Lakebase conn). Outbound to Databricks native; arbitrary internet egress per network policy.

L400Deep internals

Lifecycle

  • Create → deploy → start → update (new revision, traffic shift) → stop.

Resource resolution

  • resources: become env vars (endpoint, table, volume, Lakebase, secret, Genie Agent, AI Search index, UDF, etc.).
  • Resources must already exist; app runs with least privilege scoped to declared resources.
  • Secrets pulled from scopes at startup.
  • databricks-sdk uses injected DATABRICKS_HOST + token.

Auth paths

  • App auth: OAuth M2M, refreshable.
  • OBO: framework forwards user bearer token.
  • External APIs: secrets + outbound policy.

Compute + scaling

  • Managed container; sized CPU/memory.
  • Single-instance vertical sizing predominantly.
  • Scale-to-zero with cold-start cost.
  • Heavy compute → hand off to Jobs.

Networking

  • Same VPC/VNet (configs apply).
  • Outbound to UC/serving/Lakebase native.
  • Custom outbound via account network policy.
  • Inbound: HTTPS + OAuth.

Logs + metrics

  • stdout/stderr in UI.
  • App telemetry: declare in app.yaml to route traces, logs, and metrics to Unity Catalog tables.
  • Self-instrument for additional depth (MLflow tracing, Datadog, etc.).

Integration patterns

  • AI assistant UI on Agent Bricks.
  • Data entry forms → Lakebase / UC.
  • Internal admin dashboards.
  • Customer-facing portal (with account-level viewers).
  • Embedded apps: iframed into external websites with workspace OAuth.

Limits / realities

  • Resource sizing has caps.
  • Long-running websockets: watch idle timeouts.
  • Cold start on scale-to-zero.
  • Outbound bounded by network policy.
  • Long tasks → Jobs + poll.
  • State → Lakebase / UC.

Mental model

"Managed Heroku-like hosting with first-class Databricks integration." Best for apps acting on lakehouse + AI endpoints.

Anti-patternsWhere you should not use Databricks Apps

  • General-purpose B2C SaaS.
  • Heavy compute in-app.
  • Extensive custom infra.
  • Blocking long-running requests.
  • In-process multi-user state.
  • External SaaS dashboards.
  • Multi-third-party egress without policy.
  • Custom auth flows fighting OAuth.
  • Tens of thousands of concurrent users.
  • Hardcoded URLs/hosts bypassing resources.

WeaknessesWhere it does not do well

  • Limited runtime customisation.
  • Egress control account-level.
  • Scaling caps.
  • Cold start.
  • Logs UI basic.
  • Websocket idle timeouts.
  • OBO forwarding finicky.
  • Local dev env mismatch.
  • Basic secret rotation tooling.
  • UI versioning limited.
  • No cross-region failover.
  • DB connection pooling discipline required.
