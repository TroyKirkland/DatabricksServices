L100What it is

Compute on Databricks is Spark (with Photon acceleration) running on VMs you own (classic) or Databricks pre-warms (serverless), exposed via four shapes: all-purpose clusters, jobs clusters, SQL warehouses, and Model Serving endpoints. You pick a shape, a size, a runtime — the platform runs it.

  • Two stewardship models — classic (your VPC, cloud + DBU) vs serverless (Databricks' account, DBU-only at a higher rate).
  • One execution engine, two implementations — JVM Spark and Photon (C++ vectorized). Photon engages automatically.
  • Billed in DBU — Jobs / All-Purpose / SQL / LDP / Serverless / Model Serving each have different rates.

L200The product surface

  • All-purpose cluster — interactive notebooks/ad hoc; classic + serverless.
  • Jobs cluster — one run then teardown; classic + serverless.
  • SQL Warehouse — SQL-only compute; Serverless (default) / Pro (your VPC) / Classic (legacy).
  • LDP pipeline compute — Lakeflow Spark Declarative Pipelines; serverless default for new pipelines.
  • Model Serving endpoint — real-time CPU/GPU inference, scale-to-zero, serverless-only.

Core cluster knobs: DBR version (current LTS: 18 LTS / Spark 4.1 / JDK 21; 17.3 LTS / Spark 4.0; 16.4 LTS / Spark 3.5) · node type · autoscaling · Photon · access mode (Standard / Dedicated / No-isolation legacy) · spot mix (classic) · pools · init scripts (classic only) · cluster policy · dependency mode (beta, library management per workload) · local disk encryption (public preview, shuffle data on-disk) · AWS Capacity Blocks (reserved burst capacity).

SQL Warehouse: Serverless = seconds start, multi-tenant warm fleet, always Photon. Pro = single-tenant VPC, slower start, supports private link. Classic = legacy.

Authoring: UI, REST / Terraform / DAB YAML, Databricks Connect for local dev.

L300Architecture

          ┌────── Control plane (Databricks) ──────┐
          │ UI / REST / Scheduler / Auth / UC       │
          └──┬─────────────────────────────────┬────┘
       classic                          serverless
             ▼                                 ▼
   ┌── Customer VPC ──┐         ┌─ Databricks-owned account ─┐
   │ Driver (DBR)     │         │ Multi-tenant warm fleet     │
   │ Workers (1..N)   │         │ Driver + executor pods      │
   │ Executors+Photon │         │ NAT egress / PrivateLink in │
   └──────┬───────────┘         └──────────┬──────────────────┘
          │  reads/writes via UC short-lived creds  │
          ▼                                         ▼
              ┌──── Cloud object storage (Delta) ────┐

Two-plane model. Control plane (UI, scheduler, auth, UC) in Databricks. Data plane (driver+executors) in your account (classic) or Databricks (serverless). UC mediates all storage access via short-lived creds.

Spark exec: driver compiles plan via Catalyst+AQE, schedules tasks; executors run tasks (JVM + Photon native sidecars); shuffles via local disk+network; AQE rewrites the plan at runtime.

Photon is a separate C++ vectorized engine, dispatched per operator. Most decisive on scans, aggregations, joins, Delta reads. Python UDFs / Pandas UDFs / RDD APIs fall back to JVM.

Autoscaling: standard (reactive), enhanced (Jobs/LDP — proactive), SQL serverless (cluster-of-clusters for concurrency).

Access modes: Standard (multi-user, UC, Photon, row filters / masks) · Dedicated (single user/group, allows RDD/Scala) · No-isolation (legacy).

Cost = VM (cloud) + DBU. Serverless = DBU-only. Photon doubles the classic DBU multiplier but usually pays back via wall-clock.

L400Deep internals

What Databricks Runtime contains

  • Specific Spark build (often ahead of OSS), Photon native libs, pinned Delta, pinned JDK. DBR 18 LTS = Spark 4.1 + JDK 21; DBR 17.3 LTS = Spark 4.0 + JDK 17; DBR 16.4 LTS = Spark 3.5 + JDK 17. DBR 18 also adds SQL Scripting (GA) and state repartitioning for stateful streaming.
  • Pre-installed Python/Scala/R/Java libs (ML variant adds PyTorch / scikit / CUDA; GPU adds drivers).
  • Databricks cluster manager binaries; OS + native libs (zstd, lz4).
  • LTS = 2–3 yr support (DBR 18 LTS through June 2029); non-LTS = 6 mo. Pin LTS for production.

Photon dispatch

  • Per-operator flag set during planning. Whole Photon-supported stages run fully native, ~4096-row columnar batches.
  • Mixed stages cross JNI as Arrow batches — costs CPU; planner avoids when possible.
  • Accelerates well: Parquet scan/decode, filters, projections, aggregations, hash joins, sort, simple windows, Delta reads (DVs+stats).
  • Falls back: Python UDFs, Pandas UDFs, RDD APIs, some narrow operators. Mixing creates a perf cliff.
  • Photon has its own off-heap memory manager — separate from JVM heap. Spill via Photon spill manager.

Adaptive Query Execution (AQE)

  • Coalesces shuffle partitions; switches join strategies; handles skew via key-splitting; local shuffle reader.
  • On by default since DBR 10+. Disabling is almost always a mistake.

Dynamic File Pruning (DFP)

Pushes a small dimension's filter values into the fact-scan after first probe — prunes Parquet files at scan time. Big win on Databricks vs vanilla Spark; cheaper under Photon.

Disk cache (legacy "Delta cache")

  • SSD-backed decoded-Parquet cache on workers; auto on classic with cache-enabled instance types.
  • Serverless doesn't expose a user-visible disk cache — block/page caches at lower layers.
  • Per-cluster, lost on restart.

Cluster startup (classic)

  1. Allocate cloud VMs via provider API.
  2. Boot from Databricks-prepared image; download runtime if not on AMI.
  3. Workspace-scoped init scripts run.
  4. Driver starts; workers register; UC token agent up.

2–6 min typical. Pools cut VM-allocation; init scripts still run on attach.

Serverless internals (mental model)

  • Pre-warmed fleet, per-region.
  • Per-workload driver+executor pods in isolated network namespaces — cross-tenant impossible.
  • Egress NATs through Databricks-managed IPs; NCC controls allowlist; PrivateLink ingress supported for serverless SQL on some clouds.
  • Cold start: ~5–15s SQL warehouse, sub-minute Jobs/LDP.
  • No init scripts, no custom JARs cluster-wide, smaller Spark-config allowlist.

SQL Warehouse internals

  • Always Photon on.
  • Serverless = cluster-of-clusters. Size = worker count per cluster; cluster scaling = how many clusters spin up under load.
  • A single query never spans clusters. Multiple clusters help concurrency, not single-query latency.
  • Query history + profiles = primary debug surface (plan, stages, bytes scanned, Photon engagement, AQE rewrites).

Spark Connect / Databricks Connect

  • Client builds unresolved logical plan, ships to server.
  • Pure-Python pyspark on client; no JVM needed.
  • Notebooks behave the same in workspace or via Connect.

DBUs & billing

  • Per-second billing.
  • All-purpose > Jobs > LDP rate (varies). Picking the right shape matters more than micro-tuning configs.
  • Photon-on classic doubles the multiplier; usually a win on wall-clock.
  • Spot mix lowers cloud cost; doesn't change DBU rate. Spot reclaim retries tasks.
  • system.billing.usage = retrospective truth. Cluster tags propagate for chargeback.

Concurrency, isolation, fault tolerance

  • Driver failure is fatal — cluster restarts. Use Jobs cluster + max_retries.
  • Executor failure recoverable — Spark retries tasks. Repeated loss = spot reclaim / OOM.
  • Standard access mode isolates via UC perms but doesn't isolate compute — one user can starve others.
  • Egress: classic via your VPC NAT; serverless via Databricks-managed (optional NCC allowlist).

Hard limits / gotchas

  • Scaling to thousands of executors usually shuffles or storage IOPS-bottleneck first.
  • Init scripts >10 min time out and fail cluster start.
  • DBR upgrades aren't fully backward-compatible — pin LTS, validate next LTS in staging.
  • Serverless Spark-config allowlist is smaller than classic.
  • Python UDFs round-trip Photon→JVM→Python — common perf surprise.
  • Pool warmup not instant — cold pools take minutes to repopulate.

Mental model

"Pick the shape, pick the stewardship (classic vs serverless), pick the runtime, trust the scheduler." Spark+Photon+AQE+DFP are the same machinery everywhere. Most perf work is shape choice + Photon coverage + data layout. Debug order: wrong shape → bad data layout → Photon fallback → shuffle blowup.

Anti-patternsWhere you should not use compute like this

  • All-purpose clusters for scheduled jobs. Most expensive DBU rate. Use Jobs or serverless Jobs.
  • Long-lived "shared" clusters everyone attaches to. Noisy-neighbor; pays 24/7. Use serverless notebooks or per-user warehouses.
  • Classic SQL Warehouse for new deployments. Pro or Serverless.
  • Tiny SQL Warehouse for BI dashboards. Right-size or rely on cluster scaling.
  • Spark for sub-second OLTP. Wrong tool — Lakebase / Model Serving / KV.
  • Init scripts to install heavy native libs. Slows every start. Bake into images or use cluster libs.
  • Disabling Photon to "save money." Usually costs more in wall-clock.
  • Python UDFs in hot paths. Use SQL or Pandas UDFs.
  • Non-LTS DBR in production. Six-month support window.
  • One huge cluster for fan-out workloads. Use SQL Warehouse cluster scaling.
  • Notebook-scoped libs for a job. Pin cluster libs or DAB environments.
  • Model inference on Spark. Use Model Serving.

WeaknessesWhere compute does not do well

  • Sub-second query latency at low concurrency — overhead floor of a few hundred ms.
  • Hard real-time streaming. Structured Streaming = seconds. Use Flink/Kafka for ms SLAs.
  • Custom Spark distributions / forks. You run Databricks' Spark.
  • Limited serverless GPU. Parity gap vs classic GPU runtime.
  • Init-script-heavy classic workloads don't migrate cleanly to serverless.
  • Driver bottlenecks on plans with millions of files or huge query plans.
  • JVM tuning mostly off-limits. Driver heap configurable; deep flags not.
  • Cross-region compute doesn't exist — egress + latency to read another region.
  • Pool warmup latency under bursts.
  • Spot interruptions during shuffle-heavy stages cause big retries.
  • Photon JNI boundary can dominate cost on mixed workloads.
  • ML runtime dependency hell. Pinned versions conflict with user installs.
