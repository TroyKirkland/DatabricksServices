Lakeflow Spark Declarative Pipelines (LDP)

L100What it is

LDP is a declarative ETL framework built on Spark Structured Streaming and Delta Lake. You declare what tables should exist and how each is derived; LDP figures out the DAG, the streaming vs. batch refresh logic, the checkpoints, the retries, and the table maintenance. You write SQL or Python; you do not manage clusters, jobs, or watermarks.

  • Declarative: define tables, not pipelines. LDP composes the DAG from your CREATE STREAMING TABLE / @dlt.table declarations.
  • Streaming + batch unified: streaming tables (incremental) and materialized views (full refresh) coexist in one pipeline.
  • Production-grade plumbing free: EXPECT data quality, schema evolution, checkpoints, retries, and table maintenance all built-in.

L200The product surface

Two core table types:

  • Streaming Table (ST) — incrementally updated from a streaming source (Auto Loader, Kafka, Kinesis, UC CDF, another ST). Append-only by default; CDC merges via AUTO CDC (formerly APPLY CHANGES INTO).
  • Materialized View (MV) — fully recomputed each refresh from a deterministic query over batch sources.

Other surface:

  • AUTO CDC (current API; APPLY CHANGES INTO is the legacy form, still works but no longer recommended) — collapses a CDC stream onto an ST with SCD Type 1 or Type 2. Also supports AUTO CDC FROM SNAPSHOT (Python only) for snapshot-comparison CDC.
  • Expectations — EXPECT col > 0 with ON VIOLATION WARN | DROP | FAIL UPDATE.
  • SQL or Python authoring (@dlt.table, dlt.apply_changes(...)).
  • Triggered (run-to-completion) vs Continuous (sub-minute streaming) modes.
  • Serverless (recommended; adds incremental MV refresh) vs Classic compute.
  • UC-native: targets, lineage, audit, system tables.
  • Authored in notebooks/SQL/Py files; deployed via UI or Databricks Asset Bundles.

L300Architecture

Source(s) ──► [LDP Compile DAG] ──► [LDP Runtime on (serverless|classic) compute] ──► UC Streaming Tables / MVs
              ▲                       │
              │                       ├─ per-flow checkpoints (managed)
              │                       ├─ expectations engine (filter/warn/fail)
              │                       ├─ APPLY CHANGES merge engine
              │                       └─ table maintenance (OPTIMIZE/VACUUM)
       Your SQL/Python notebooks
       (CREATE STREAMING TABLE, @dlt.table)

On each update, LDP:

  1. Parses source files, resolves LIVE.<name> references, builds the DAG.
  2. Validates: cycles, missing tables, schema compatibility, permissions.
  3. Plans each flow as a streaming or batch query. Streaming flows get a managed checkpoint dir under the pipeline's storage root.
  4. Runs flows in dependency order; independents in parallel; streaming flows execute as micro-batches under a Spark application.
  5. Applies expectations at materialization. Drop filters out, warn logs to event_log, fail aborts and retries.
  6. Maintains tables: serverless via Predictive Optimization; classic via a periodic maintenance task.

Compute: Classic = sized cluster with enhanced autoscaling. Serverless = managed pool with per-flow autoscale; adds incremental MV refresh and stream pipelining.

Schema evolution: new columns auto-add (where source supports). Type changes need FULL REFRESH. MVs reflect query schema on each refresh.

UC integration: targets must be UC. Lineage, permissions, audit, and system tables are native.

L400Deep internals

Pipeline graph + flow concept

  • A "flow" is the atomic unit of work: one writer into one target. A table can have multiple flows (e.g., APPLY CHANGES INTO + an APPEND FLOW).
  • The DAG is rebuilt from source on every update. No persistent DAG schema.
  • Topological execution; independent subtrees run concurrently.

Checkpoint management

  • Each streaming flow owns <pipeline_storage>/checkpoints/<flow_id>/. Managed by LDP.
  • Checkpoints survive code edits as long as the target table identity is unchanged. Renaming detaches → effectively full refresh.
  • FULL REFRESH deletes the checkpoint and (for STs) truncates the target before reprocessing.
  • Watermarks declared via withWatermark() or WATERMARK col DELAY OF '...'; state retention follows.

Expectations engine

  • Modes: DROP ROW, WARN (default), FAIL UPDATE.
  • Implemented as Spark expressions appended to the flow's writer plan; counts emitted to event_log per micro-batch.
  • FAIL UPDATE aborts + retries; repeated failures park the pipeline.

AUTO CDC mechanics (formerly APPLY CHANGES INTO)

AUTO CDC is the current recommended API; APPLY CHANGES INTO uses identical syntax but is no longer the recommended form.

  • Compiles to a merge plan: consume change feed → dedupe by KEYS (...) and SEQUENCE BY <col> → apply I/U/D to target.
  • SCD Type 2 adds __START_AT / __END_AT and back-dates the prior current row.
  • Idempotent on (key, sequence). Out-of-order events handled within watermark; outside it, late events may drop.
  • Bitemporal tracking (Beta): extends SCD Type 2 to track changes across both business time and system time.
  • Partial updates: change records can update only a subset of columns.
  • Version functions: explicit control over snapshot ordering for out-of-order arrivals.
  • AUTO CDC FROM SNAPSHOT (Python only): compares sequential full snapshots to infer inserts/updates/deletes — no change feed required. Note: expectations are not supported with this form.

Materialized view refresh

  • Classic: full recompute each update.
  • Serverless: LDP analyses query; computes incremental MV refresh when supported, else full. Supported-operator list is documented.

Event log

  • Per-pipeline event_log view (UC table): flow lifecycle, micro-batch metrics, expectation violations, schema changes, autoscaling, maintenance.
  • Primary observability primitive — build alerts off this, not driver logs.

Maintenance

  • Both compute flavors run table maintenance: OPTIMIZE, VACUUM, liquid-clustering opt, predictive optimization analysis.
  • Serverless defers to Predictive Optimization for managed tables.

Limits and operational realities

  • One pipeline can launch multiple Spark contexts (serverless). Don't rely on shared in-memory state.
  • Two pipelines writing the same target → conflicts. Use @dlt.append_flow within one pipeline for multi-source-to-one-table.
  • Python UDFs run on the cluster; serverless restricts library install to top-of-notebook %pip install; no init scripts.
  • pipelines.notifications wires Slack/email alerts.
  • DBSQL streaming tables / MVs are backed by hidden LDP pipelines.

Mental model

LDP is "Spark Structured Streaming + Delta + a DAG planner + a maintenance scheduler" hidden behind declarative table definitions. The thing it uniquely owns is the per-flow checkpoint + expectation + maintenance lifecycle, and the planner that decides when to incrementally refresh an MV. Everything else you could (painfully) write yourself in Spark.

Anti-patternsWhere you should not use LDP

  • Arbitrary Python jobs. LDP is for declared tables. Random "read this, call an API, write a CSV" belongs in a notebook task in Lakeflow Jobs.
  • One-shot transforms. Overkill. Use a SQL task or a notebook.
  • Heavily imperative logic. Loops, branches, dynamic table names — LDP wants a static DAG. Drive LDP from a parent Job for control flow.
  • Non-Delta sinks. LDP writes UC STs and MVs only. Forwarding to Snowflake/Kafka/HTTP → use Structured Streaming directly.
  • Hot-path / sub-second pipelines. Smallest unit is a micro-batch. Sub-second event handling → Structured Streaming + foreachBatch, or Zerobus.
  • Cross-pipeline writes to the same table. Two pipelines on one target = race. Use @dlt.append_flow in one pipeline.
  • Interactive exploration. Develop in notebooks; port to LDP when productionising.
  • Heavy external libraries on serverless. Library install is restricted. Use classic LDP or a Job.
  • Hand-tuned per-flow cluster sizing. Autoscale is pipeline-wide.
  • Pure event forwarding. If you don't need data in Delta, LDP is the wrong layer.

WeaknessesAreas LDP does not do well

  • Dev loop friction. Start → validate → run is much slower than running a notebook cell. Use dev-mode + small datasets.
  • Debugging opacity. Generic Py4J / Spark exceptions; stack traces don't always pinpoint your line.
  • Schema evolution gaps. Adds: yes. Renames: no. Type changes: FULL REFRESH.
  • MV incremental refresh isn't universal. Many queries fall back to full recompute on serverless.
  • Continuous cost surprises. 24/7 pipelines burn DBUs even when idle. Triggered + scheduled is usually cheaper.
  • Cross-pipeline coordination. No first-class chaining; orchestrate via Lakeflow Jobs.
  • Local testing is awkward. No local executor; only orchestration runs on Databricks.
  • Streaming source breadth. First-class: Auto Loader, Kafka, Kinesis, EventHubs, UC CDF, ST. Others need custom Spark sources.
  • AUTO CDC needs a sequence. If your source can't emit one, manufacture one or fall back to SCD Type 1. AUTO CDC FROM SNAPSHOT avoids this constraint but loses expectations support.
  • UDF cost. Python UDFs are row-at-a-time JVM↔Python boundary; prefer SQL or pandas UDFs.
  • Layered settings. Pipeline / table / flow / cluster-policy overrides interact in non-obvious ways.
