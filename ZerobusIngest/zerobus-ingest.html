L100What it is

Zerobus is a gRPC SDK that writes events directly into a Delta table in Unity Catalog, without a Kafka / Kinesis hop. Generate a Protobuf schema from your UC table, embed the client into your producer, send() events.

  • Direct-to-Delta: no broker.
  • Low latency: sub-second p99 in the right config.
  • Multi-language: Python, Java, Go, TypeScript, Rust.

L200The product surface

  • Producer SDK: ZerobusClient + send(event) / send_batch().
  • Protobuf schema generated from UC table.
  • ACK semantics: future/promise per send; fire-and-forget or wait-on-ack.
  • At-least-once default; client-side dedup keys for effective-once.
  • UC governance on the destination table.
  • Schema evolution: add column → regen proto → producer recompile.
  • Auth: service principal OAuth M2M or PAT.

L300Architecture

Your app
   │   (Zerobus SDK, gRPC)
   ▼
Databricks Zerobus endpoint ──► [batching, compression, dedupe] ──► Delta table (UC managed)
                                                                     │
                                                                     └── predictive optimization, OPTIMIZE/VACUUM (UC)

Long-lived gRPC + HTTP/2. Server batches events and commits to Delta in throughput-optimised micro-batches. ACK = event durable in Delta log. Downstream: Photon, OPTIMIZE, time-travel, Delta Sharing all apply.

L400Deep internals

Wire protocol

  • gRPC schema-driven; per-table endpoint URL.
  • Proto message generated from UC schema; field numbers = columns.
  • Client-streaming RPC; server-streaming ACKs back.

ACK + ordering

  • ACK = durable in Delta.
  • Per-stream ordering preserved.
  • Across streams: best-effort. Single-stream + await-per-send = strict order, lower throughput.

Throughput + batching

  • Pipeline sends (no await between) for peak throughput.
  • Commits trigger on time- or size-bound; latency floor ~1s in default tuning.
  • Per-table commit ceiling; shard for huge fan-in.

At-least-once vs exactly-once

  • Default at-least-once. Network retries can double-write.
  • Effective exactly-once via client dedup key + downstream APPLY CHANGES INTO.

Schema evolution

  • Add column → new proto field; old producers fine.
  • Drop / rename / type narrow → coordinated redeploy.

Networking

  • gRPC TLS on standard endpoints. Private Link supported.
  • Cross-cloud producers pay WAN egress.

Failure modes

  • Backpressure manifests as send-latency growth.
  • Reconnect with backoff; resume from last-ACKed offset client-side.
  • Databricks restart does not lose ACKed data.

Limits / realities

  • Bounded max event size (MBs).
  • Per-table throughput ceiling; shard for multi-million-eps.
  • Schema must be proto-representable.
  • Zerobus is write-only; reads are normal Delta.

Mental model

Kafka producer → Delta with the broker removed. Best for high-volume event capture into the lakehouse where you don't need broker-style consumer fan-out.

Anti-patternsWhere you should not use Zerobus

  • Need broker fan-out. Multiple independent consumers → Kafka/Kinesis.
  • Sub-millisecond latency. Use in-process buffers or real-time engines.
  • Sources you don't own. No SDK in source → use Lakeflow Connect or Kafka.
  • Tiny volumes. Nightly 10K rows → COPY INTO.
  • Topic replay required. Delta isn't a Kafka log; build CDF reader.
  • Strict global ordering across producers. Need single producer (often impractical).
  • Heavy in-flight transforms. Transform downstream in LDP.
  • Cross-region high-volume producers. WAN egress.
  • ACK-on-consumed required. ACK is on-Delta-commit only.
  • Mobile / browser clients. Backend / service-side only.

WeaknessesWhere it does not do well

  • No consumer pull semantics. Delta is the only "consumer".
  • Per-table commit throughput ceiling. Shard for huge fan-in.
  • Non-additive schema changes cascade. Renames, type narrows, drops force producer redeploy.
  • Limited replay tooling. Query Delta CDF or time-travel.
  • At-least-once requires dedup discipline. No native cross-retry exactly-once.
  • Opaque backpressure. Latency grows; reasons not always surfaced.
  • Less ecosystem vs Kafka. No Connect, no kSQL, lighter registry.
  • WAN cost / latency for cross-cloud.
  • UC managed Delta only. No non-Delta sink.
  • SDK maturity varies. Python/Java mature; TS/Go/Rust trailing.
  • Client-side metrics on you. Export to your stack.
  • No native partitioning beyond table partition column.
