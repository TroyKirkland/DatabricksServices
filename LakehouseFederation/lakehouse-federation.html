L100What it is

Query other databases as if they were UC tables — no copy. Two modes: Query Federation (JDBC pushdown to relational databases) and Catalog Federation (direct object-storage reads for platforms with open catalog services). Both surface as foreign catalogs in UC.

  • No copy: live source reads.
  • UC-governed.
  • SQL-anywhere: lakehouse + external in one query.

L200The product surface

  • Connection: UC securable with type/host/credentials.
  • Foreign catalog: mirrors source schemas; read-only mostly.
  • Query Federation sources (JDBC): PostgreSQL, MySQL, SQL Server, Azure Synapse, Snowflake, Redshift, BigQuery, Salesforce Data 360, Oracle, Teradata, Databricks.
  • Catalog Federation sources (object storage): Legacy/External Hive metastore, AWS Glue, Salesforce Data 360, Snowflake, Palantir Foundry, Workday Data Connect.
  • HTTP connection type: new (Runtime 16.2+).
  • Pushdown: filters, projections, aggregates when possible (Query Federation).
  • Catalog Federation auto-refreshes schema at query time; Query Federation needs manual refresh.
  • UI / SQL CREATE CONNECTION / API / Terraform / DABs.

L300Architecture

Query Federation:

[Spark/DBSQL] ─► [UC Foreign Catalog] ─► [JDBC connector] ─► [External DB] ─► rows ─► Spark

Catalog Federation:

[Spark/DBSQL] ─► [UC Foreign Catalog] ─► [External catalog metadata] ─► Databricks reads object storage directly

UC owns the credential. Query Federation: Catalyst negotiates pushdown; unpushed work pulls rows into Spark. Catalog Federation: Databricks reads object storage directly — no JDBC round-trip, more cost-efficient. Permissions: UC grants + connection identity at source.

L400Deep internals

Pushdown coverage

  • Always: simple WHERE, projections, LIMIT, single-table aggs on common functions.
  • Often: same-source joins, common window functions.
  • Rarely: UDFs, Photon-only funcs, cross-source joins.
  • EXPLAIN reveals pushed predicates. Failure-to-push pulls rows — the silent perf killer.

Cross-source joins

  • Two separate scans + join in Spark. Filter aggressively first.

Credential management

  • Connection stores creds encrypted in UC.
  • Source-side identity = connection identity. Per-user requires OAuth federation per source.

Query lifecycle

  • Parse → resolve via UC FC metadata cache → plan with source pushdown rules → execute → stream rows.

Per-source quirks

  • Snowflake: Query Federation (JDBC, warehouse cost per query) or Catalog Federation (object storage, more cost-effective). Not all Snowflake functions map.
  • Postgres/MySQL/SQL Server: solid JDBC pushdown; for hot paths, prefer Lakeflow Connect CDC.
  • BigQuery: JDBC pushdown; large pulls expensive (slots).
  • Redshift: unloads via temp S3 in some setups.
  • Salesforce Data 360: Query Federation or Catalog Federation; rate-limit-aware.
  • Oracle / Teradata: Query Federation (GA as of 2026).
  • Palantir Foundry / Workday Data Connect: Catalog Federation only.
  • AWS Glue / Hive metastores: Catalog Federation; primary use case is incremental UC migration.

Caching and schema refresh

  • No first-class FC result cache; DBSQL warehouse cache may apply.
  • Catalog Federation: schema refreshed automatically at query time. Query Federation: manual refresh on source schema changes.
  • For repeat workloads, materialise to Delta.

Limits / realities

  • Catalog refresh on schema change may be manual.
  • Mostly read-only; writes limited.
  • Cost has two sides; attribution messy.
  • Vendor type quirks (VARIANT, STRUCT).
  • Cross-region egress hurts.

Mental model

Two tools in one: (1) Query Federation — JDBC pool with UC governance and pushdown; (2) Catalog Federation — zero-copy metadata bridge for open-format catalogs. Best for discovery, governed access, incremental UC migration, POC. Worst for hot production paths where copy-then-query is faster.

Anti-patternsWhere you should not use Federation

  • Production batch ETL. Mirror via Lakeflow Connect.
  • Hot dashboards. Mirror first.
  • Sub-second OLTP.
  • High-fan-out cross-source joins.
  • Write-heavy operations.
  • Source-side compute cost sensitive.
  • Sources behind unreliable networks.
  • Real-time streams.
  • Permanent architecture. Use to scope, then mirror.
  • Cross-region without egress budget.

WeaknessesWhere it does not do well

  • Pushdown coverage uneven.
  • Per-user source identity hard.
  • Schema refresh varies by mode. Catalog Federation auto-refreshes; Query Federation needs manual refresh.
  • Limited writes.
  • Weak result caching.
  • Lineage stops at edge.
  • Type fidelity issues.
  • Split cost attribution.
  • Source audit shows one user.
  • Throughput = source.
  • Extra setup per source.
  • No cross-source join pushdown.
