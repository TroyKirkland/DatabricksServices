# Databricks Product Docs

An L100 → L400 reference set for every major Databricks product — written by a field engineer, for field engineers. Anti-patterns and weaknesses called out next to capabilities. No marketing fluff.

> **Author:** Troy Kirkland · troy.kirkland@databricks.com
> **Status:** Personal field-engineering notebook. Based on public Databricks documentation. Not an official Databricks publication and does not represent Databricks' positions.

## 🌐 Read it as a site

If you have GitHub Pages enabled for this repo, the rendered site lives at:

```
https://<owner>.github.io/databricks-product-docs/
```

Otherwise: clone the repo and open `index.html` in a browser — every link is relative, so it works fully offline.

```bash
git clone <repo-url> && cd databricks-product-docs
open index.html      # macOS
xdg-open index.html  # Linux
```

## 📖 What's inside

| Area | Where |
|---|---|
| **Per-product L100–L400 docs** | One folder per product (PascalCase), e.g. `DeltaLake/delta-lake.{md,html}`. ~28 products, listed in `_control.yaml`. |
| **Cross-cutting topics** | `Storage/` and `Compute/` — syntheses across multiple products. |
| **Glossary** | `Glossary/glossary.{md,html}` — shared term definitions, linked from every product doc via `[[glossary:term]]`. |
| **Product Evolution** | `ProductEvolution/product-evolution.png` — visual timeline of launches, renames, sunsets, acquisitions, and multi-rename chains. |
| **Per-product feature timelines** | `ProductEvolution/by-product/*.png` — month-by-month GA / Public Preview / Beta milestones, auto-scraped from `docs.databricks.com`. |

Every product doc follows the **same** structure: **L100** (what it is) → **L200** (product surface) → **L300** (architecture) → **L400** (deep internals) → **Anti-patterns** → **Weaknesses** → **Sources**.

## 🔄 Refreshing the feature timelines

The per-product feature timelines under `ProductEvolution/by-product/` are generated by a tiny stdlib-only Python pipeline:

```
feature-scraper.py       fetch docs.databricks.com release notes  →  features-12mo.json
feature-classifier.py    bucket each event into a product family  →  features-classified.json
feature-timeline.py      one SVG+PNG per bucket                    →  by-product/*.png
refresh.sh               one-shot orchestrator
```

Refresh weekly or monthly:

```bash
cd ProductEvolution
./refresh.sh                   # last 12 months; auto-commits + pushes if anything changed
./refresh.sh 2025-01 2026-05   # explicit range
./refresh.sh --local-only      # preview only; skip git commit + push
```

The refresh **only commits when the data actually changed** — feature-timeline.py stamps the SVG header with the latest event date in the dataset (not `datetime.now()`), so re-running on identical input produces zero diff. Staging is scoped to `features-*.json` and `by-product/` only, so any in-flight edits elsewhere are left alone.

For **LLM-quality classification** (vs the keyword fallback), set an Anthropic key:

```bash
export ANTHROPIC_API_KEY=sk-ant-...
./refresh.sh
```

Cost is approximately $0.01 per refresh on Haiku 4.5. The keyword fallback is free but leaves more events in the "other" bucket and produces some obvious misclassifications.

## ✏️ Contributing / extending

The doc set is controlled by `_control.yaml`. To add a product or topic:

1. Append an entry to `_control.yaml` under `products:` (or `topics:` for pipeline-style artefacts).
2. Set `status: pending`.
3. Generate the L100–L400 doc following the template in `_control.yaml` and the canonical example at `DeltaLake/delta-lake.md`.
4. Add a card to `index.html` (Cross-cutting Topics or the appropriate category) and a matching line to `index.md`.
5. If the new product belongs to an existing feature-timeline bucket, add a `Feature timeline ↗` link to its card pointing at `ProductEvolution/by-product/{bucket}.png`. If it's a new bucket, also extend `feature-classifier.py:TAXONOMY` and `feature-timeline.py:BUCKET_TITLES`.

PRs welcome — fork freely. Sources should be public Databricks docs only — no internal Slack quotes, customer details, or unreleased product info.

## 🛠 Tooling notes

- **No mermaid-cli.** `mmdc` hangs on Chrome launch on macOS with current Puppeteer / Chrome 148. All diagrams are hand-authored SVG, converted to PNG via:
  ```
  brew install librsvg
  rsvg-convert -w 2400 input.svg -o output.png
  ```
- **Python 3.10+ stdlib only.** No `pip install` needed. The pipeline scripts use `urllib`, `re`, and `json` — works in any environment with a recent Python.
- **GitHub Pages compatibility.** A `.nojekyll` file at the repo root is required because `_style.css` and `_control.yaml` start with `_`, which Jekyll would otherwise hide. Don't remove it.

## 📐 Conventions

- Folders: `PascalCase` (e.g. `LakeflowConnect/`)
- Files: `kebab-case` (e.g. `lakeflow-connect.md`)
- Each product: parallel `.md` + condensed `.html`
- Cross-references between docs: `[[glossary:term]]` in markdown, hyperlinked in HTML
- Voice: field-engineer technical, opinionated, no marketing fluff
