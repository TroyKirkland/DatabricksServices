L100What it is

Multi-party data collaboration where only approved queries (or trusted provider code) run on shared data and only aggregate / sanitized results come out. UC-native. Two models:

  • Approval-based: all collaborators equal; every notebook approved unanimously before running.
  • Packaged (GA July 2026): provider-consumer — provider's code hidden from consumer; no approval workflow required.
  • UC + Delta Sharing under the hood.

L200The product surface

  • Clean room: UC object; max 10 collaborators; locked after creation.
  • Approval-based model: equal privileges; unanimous notebook approval + optional auto-approval rules.
  • Packaged model (GA July 2026): provider-consumer; provider code hidden; consumer runs without code review.
  • Collaborators identified by Databricks metastore or Delta Sharing identity.
  • Contributed assets: tables, views, volumes (same cloud/region only). Read via Delta Sharing; no persistent copy.
  • Serverless egress control: restrict outbound network from sandbox.
  • Output bindings: per-collaborator UC tables.
  • Optional differential privacy.
  • Full audit of contributions, approvals, runs, outputs.

L300Architecture

[Org A UC] tables ─┐
                   ├─► [Clean Room (UC obj) approved tasks, serverless compute] ─► Outputs → A and/or B
[Org B UC] tables ─┘

Compute in UC-isolated serverless sandbox: no shell, no egress, only approved code. Data flows via Delta Sharing for run duration. Outputs to pre-agreed UC tables. All actions logged.

L400Deep internals

Approval model (approval-based rooms)

  • Tasks proposed → all collaborators approve → sealed; edits re-trigger approval.
  • Auto-approval rules: configure conditions for automatic re-approval of task updates.
  • Audit logs each approval.

Packaged clean rooms (GA July 2026)

  • Provider authors notebooks/JARs + contributes data; consumer contributes their data.
  • Provider code + assets hidden from consumer — consumer sees only names, not code.
  • No approval workflow; consumer trusts provider. Only consumer sees run outputs.
  • Review egress network policy: ensure provider code cannot exfiltrate consumer data.

Sandbox execution

  • Serverless, isolated; configurable egress control via serverless egress policies.
  • Clean-room identity has READ on contributed data, WRITE only to output bindings.
  • Logs minimised beyond approved structured outputs.

Differential privacy

  • Noise injection on aggregates; epsilon budget per query.
  • Budget exhaustion blocks further queries.
  • Not always required — approval review can substitute.

Output bindings

  • (target table, metastore, schema) tuples.
  • Per-collaborator visibility configurable.
  • Delivered via Delta Sharing.

Cross-cloud / cross-region

  • Works cross-cloud via Delta Sharing.
  • Compute in owner region; cross-region pays egress.
  • Volumes not accessible cross-cloud or cross-region — only default-storage tables available in those configurations.

Limits / realities

  • Approval cycles add latency.
  • Code must be reviewable; opaque ML harder.
  • Pre-approved library set conservative.
  • Result-size caps prevent disguised raw exfiltration.
  • Audit archival is critical.

Mental model

"Sealed lockbox where two parties' data meets, only approved code looks inside, only approved aggregates come out."

Anti-patternsWhere you should not use Clean Rooms

  • Internal single-org use. Use UC row/column + ABAC.
  • Free-form exploration. Every query needs approval.
  • Hot-path queries. Minutes, not seconds.
  • Tiny / uniform datasets. DP can't save you from re-identification risk.
  • Replace a DPA. Technical, not legal.
  • Full warehouse delivery. Use Delta Sharing.
  • Custom Python with private libs. Approval friction.
  • Petabyte cross-cloud.
  • One-shot analyses. Overhead too high.
  • PII laundering. Legal rules still apply.

WeaknessesWhere it does not do well

  • Approval friction.
  • Library restrictions.
  • Debugging hard in sealed sandbox.
  • Conservative DP budget.
  • Rigid output schemas.
  • Cross-org review SLAs.
  • Limited compute tuning.
  • Heavier cross-cloud setup.
  • High audit volume.
  • No interactive REPL.
  • Cost-attribution is contractual.
  • Task versioning needs discipline.
