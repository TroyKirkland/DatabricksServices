L100What it is

DBSQL is the lakehouse data warehouse surface: serverless SQL warehouses, SQL editor, dashboards, alerts, query history. ANSI SQL over UC tables; engine is Photon-accelerated Spark SQL on Delta.

  • Warehouses: Serverless / Pro / Classic.
  • ANSI SQL + extensions: ai_query, pipe syntax, geo.
  • Lakehouse-native BI: query, share, schedule, alert, dashboard.

L200The product surface

  • Warehouses: Serverless (recommended), Pro (in-VPC governance), Classic (legacy). Size 2X-Small → 4X-Large; multi-cluster autoscale; idle auto-stop.
  • SQL editor: multi-tab, params, history.
  • Queries (saved, parameterised) consumed by dashboards/alerts.
  • Dashboards (AI/BI), Alerts (email/Slack/webhook).
  • Statement Execution API (REST, inline/arrow/external-links).
  • JDBC/ODBC for BI tools.
  • AI Functions: ai_query, ai_classify, ai_extract, ai_gen.
  • Pipe syntax, recursive CTEs, multi-statement txns, stored procedures (GA, Runtime 17.0+/UC only), MVs, STs, read_files(), http_request(), Federation.
  • Metric Views: semantic-layer business metrics defined in UC; queryable via MEASURE aggregate; surface in dashboards and Genie Agents.

L300Architecture

[BI / SQL editor / API] ─► [SQL Warehouse cluster] ─► [Photon SQL engine] ─► UC tables (Delta + Federation)

Warehouse = long-lived autoscaling Spark cluster tuned for SQL. Photon on by default. Three caching layers: result cache, disk cache (NVMe), query plan cache. Multi-cluster mode scales on queue depth. UC enforces row/column policies; lineage logged.

L400Deep internals

Warehouse lifecycle

  • States: stopped → starting → running → stopping. Serverless start ~5–15s; Pro 60–180s.
  • Auto-stop after idle (1+ min on serverless).
  • Multi-cluster: min_num_clusters→max_num_clusters on queue depth.
  • Size = workers/memory per cluster; bigger size = faster per query, not more concurrency.

Result + disk cache

  • Result cache keyed on (SQL text + UC table version + params); ms-latency hits; invalidated on table change.
  • Disk cache = NVMe-cached Parquet/Delta decoded form; lives with worker.
  • Photon stats + min/max pruning is the cold-cache layer.

Query lifecycle

  • Parse → resolve (UC + policies) → optimise → execute (Photon) → stream/spill to cloud-fetch.
  • Logged in system.query.history.

Statement Execution API

  • POST /api/2.0/sql/statements.
  • Formats: inline / arrow stream / EXTERNAL_LINKS (large).
  • Async-friendly; poll if needed.

Federation in DBSQL

  • Foreign catalogs proxy queries; pushdown best-effort.
  • Failed pushdown pulls data; federated joins can be heavy.

AI Functions

  • ai_query(endpoint, prompt|col) calls Model Serving.
  • Latency dominated by endpoint; rate-limit aware.
  • Token usage routes through Unity Gateway (formerly Mosaic AI Gateway) when configured.

STs + MVs in DBSQL

  • Backed by hidden LDP pipelines.
  • CREATE STREAMING TABLE, CREATE MATERIALIZED VIEW.

System tables

  • system.query.history, system.compute.warehouses, system.billing.usage for cost.

Limits / realities

  • Result rowset cap; use EXTERNAL_LINKS for big results.
  • Statement Execution rate limits per workspace.
  • Bursty workloads queue; size up or multi-cluster.
  • ai_query rate-limited by endpoint.
  • Stored procedures GA (Runtime 17.0+, UC only); language semantics differ from legacy procedural SQL.

Mental model

Serverless data warehouse on UC + Delta + Photon. Differentiators vs Snowflake/BigQuery: cheap pause; UC governance; SQL+Spark feature parity; AI functions; JDBC/ODBC.

Anti-patternsWhere you should not use DBSQL

  • Heavy ETL transforms. Use LDP/notebooks.
  • Long-running interactive Python. Notebooks.
  • Single-row OLTP. Use Lakebase.
  • AI batch over millions of rows via ai_query. Spark/LDP + Model Serving batch.
  • Repeat federated reads. Mirror via Lakeflow Connect.
  • Oversized warehouses "just in case".
  • Classic warehouses for new work.
  • Long-held JDBC over idle warehouses.
  • Streaming billion-row results to a client. External links or UC table.
  • Mixing prod + dev on one warehouse.

WeaknessesWhere it does not do well

  • Serverless cold start still measurable.
  • Multi-cluster scales on queue depth. Bursts queue first.
  • No inline Python in queries.
  • Stored procedures require Runtime 17.0+ / UC only. Language semantics differ from legacy procedural SQL.
  • Result-cache invalidation coarse.
  • Federated joins uneven.
  • JDBC driver quirks across BI tools.
  • Per-query cost needs system tables.
  • ai_query rate limits surface as failures.
  • No cross-warehouse handoff.
  • Streaming-table refresh is opaque.
  • Multi-statement txn is limited.
