L100What it is

Feature store on UC. Compute features offline as Delta tables; optionally publish to online tables for inference. Training-serving parity + point-in-time correctness for batch training.

  • Feature tables = Delta + PK + (optional) timestamp.
  • Online tables = low-latency replicas synced from offline.
  • Training set logging ties model versions to features.

L200The product surface

  • Feature table: Delta + declared PK + optional timestamp.
  • Online table: synced low-latency replica.
  • Python client databricks-feature-engineering: create, log, lookup.
  • Training set via fe.create_training_set with point-in-time joins.
  • Inference lookup auto or manual via feature serving endpoint.
  • Feature Views (Public Preview, DBR 17.0 ML+): declarative feature definitions; sources: DeltaTableSource, StreamSource (Kafka ~200ms p99), RequestSource; define once, materialise to offline or online stores.
  • UC lineage feature → model → endpoint.

L300Architecture

[Source] → [Feature pipeline] → [Feature table (Delta, UC)]
                                       ├ Training: point-in-time join → training set → MLflow run
                                       └ Online sync via CDF → online table → low-ms lookup at inference

Offline pipeline is yours; online sync managed. Model logged with feature deps; serving auto-looks up if configured.

L400Deep internals

Feature table conventions

  • Declare PK + optional timestamp column.
  • Schema add freely; remove rebuilds online.

Point-in-time join

  • (entity_id, event_ts, label) + FeatureLookup(table, key, ts, cols) → latest-as-of-event-time row.
  • Avoids label leakage.
  • Multi-table independent timestamp grids.

Online tables

  • Backed by Lakebase Autoscaling projects (Databricks-managed).
  • Three sync modes: triggered (scheduled incremental), continuous (streaming CDF), snapshot (one-time bulk).
  • Up to 3 read replicas for HA and load distribution.
  • Low-ms read at inference.
  • Constraint: cannot create new endpoints that look up from multiple online feature stores on Lakebase Autoscaling instances; existing ones grandfathered.

Feature Views (Public Preview)

  • Declarative feature logic: define aggregations and transforms once; framework materialises to offline + online.
  • Sources: DeltaTableSource, StreamSource (Kafka, ~200ms p99), RequestSource (request-time scalars).
  • Requires DBR 17.0 ML or above / serverless. Enable from Previews page.

Training-time logging

  • fe.create_training_set + fe.log_model attach feature spec to MLflow run + model.

Inference

  • Logged model with feature deps can auto-lookup at Model Serving.
  • Or manual via feature serving endpoint.

Feature serving endpoints

  • REST /serving-endpoints/<feature>/invocations with PK payload.

Limits / realities

  • Lakebase Autoscaling backing cost.
  • >1 TB tables need partial publishing.
  • PK changes = full re-sync.
  • Point-in-time joins are Spark-heavy.
  • No native pipeline orchestration; use Jobs + LDP.
  • Per-lookup custom transforms aren't built-in.
  • Cannot create new endpoints with multiple online feature stores on Lakebase Autoscaling; existing ones grandfathered.

Mental model

"Declare features once, govern, train+serve from one definition." Point-in-time correctness + same-features-at-serving are the load-bearing benefits.

Anti-patternsWhere you should not use Feature Engineering in UC

  • One-shot training. Join inline.
  • Non-feature tables. Just use UC tables.
  • OLTP-scale lookup. In-process cache or global KV.
  • Daily-changing features. Defeats the point.
  • Time-series without timestamp. Label leakage.
  • Embeddings as features. Use Vector Search.
  • Compute at lookup time.
  • Custom transforms in lookup.
  • Online for huge rarely-read tables.
  • Generic data API role.

WeaknessesWhere it does not do well

  • Online table cost.
  • Seconds-scale sync lag.
  • No multi-region online.
  • PK-change re-sync.
  • Orchestration on you.
  • Reproducibility by convention.
  • Slow first-sync backfill.
  • Limited transform hooks.
  • Cross-team reuse needs governance.
  • No first-class monitoring dashboard.
  • Workspace→UC migration effort.
  • Manual staleness tracking.
  • Cannot create new multi-online-store endpoints on Lakebase Autoscaling. Existing grandfathered; new designs must consolidate.
