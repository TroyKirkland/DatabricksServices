L100What it is

Lakeflow Jobs is the orchestrator for Databricks. It runs DAGs of tasks (notebooks, Python wheels, SQL, LDP pipelines, dbt, JARs) on a schedule or trigger, with retries, notifications, and observability.

  • Native orchestrator for everything Databricks: notebooks, Python, SQL, LDP, dbt, ML.
  • Triggers: cron, continuous, file arrival, table update, manual, API.
  • Resilient by default: per-task retries, repair runs, conditional execution, notifications.

L200The product surface

Core primitives:

  • Job — DAG of tasks with name, owner, permissions, triggers, run-as identity.
  • Task — DAG node. Types: notebook, Python script, wheel, JAR, SQL (query/dashboard/file/alert), LDP pipeline, dbt, run-job, if/else, for-each, condition.
  • Dependencies — declared between tasks; status-aware (Success / All Done / At Least One Success).
  • Triggers — cron, continuous, file arrival, table update, manual, API.
  • Compute — per-task choice: job clusters, all-purpose, serverless jobs compute, SQL warehouses.
  • Run-as identity — service principal or user; controls UC permissions for the run.
  • Parameters — job- and task-level; passed via widgets, SQL param binding, or CLI args.
  • TaskValues — tiny key/value emit/read between tasks.
  • Repair run — re-run only failed tasks.
  • Notifications — email, Slack, Teams, PagerDuty, webhook.
  • Authored via UI, REST/SDK, Terraform, or Databricks Asset Bundles.

L300Architecture

Trigger ──► Job run ──► Task graph ──► Task runs (each on its own compute)
                       │                ├─ retries / repair scope
                       │                ├─ TaskValues bus
                       │                └─ event/log emission to system.workflow
                       └─ notifications, lineage to UC

Control plane orchestrates; tasks run on chosen compute. A job can mix compute types per task. Tasks have retries, timeouts, dependency-and-status edges. Conditional via if/else, fan-out via for_each. Run history lives in system.workflow.*.

L400Deep internals

Run lifecycle

  • Job run has run_id globally unique within workspace; task run has task_run_id.
  • Runs queue briefly when over concurrent-run cap (per-workspace, adjustable).
  • Task records state/result_state/cluster instance/error.

Compute & DBU implications

  • Job clusters — cheapest DBU SKU; ephemeral; cold-start amortised when tasks share.
  • All-purpose — most expensive SKU; avoid for production.
  • Serverless jobs compute — fast startup, scale-to-zero, often cheapest net.
  • SQL warehouses — SQL tasks bill the warehouse SKU.

TaskValues mechanics

  • Scoped <run_id, source_task_key, key>; size cap ~48 KB.
  • dbutils.jobs.taskValues.get(taskKey, key). Throws unless default supplied.
  • Don't pass data — pass UC table names.

Retries and repair

  • Retries rerun a single task within the same run.
  • Repair run inherits prior state, re-executes failed + downstream-of-failed.

Triggers — depth

  • Cron (quartz, timezone pinnable). Continuous (at-most-one re-trigger). File arrival (UC volume / cloud path). Table update (UC version increment). API (POST /api/2.2/jobs/run-now).

Permissions and run-as

  • UC checks resolve against run_as, not the trigger caller. View / Manage Run / Manage / Owner are separate.

System tables

  • system.workflow.job_run_timeline, job_task_run_timeline, jobs — source of truth for cost and SLA dashboards.

Limits / realities

  • 1,000 tasks per job (hard limit). For larger DAGs, use sub-jobs via run-job tasks. For-each parallelism is separately capped.
  • Per-workspace cap: 2,000 concurrent task runs (429 when exceeded), 12,000 saved jobs. 2.2 API supports webhook-style notifications.
  • Continuous + failing task without max_failures = retry storm.
  • Task state should land in UC, not /tmp.

Mental model

Lakeflow Jobs is a workspace-native Airflow with first-class Databricks task types and tight UC + system-table integration. Less extensible than Airflow, more native to Databricks compute/lineage/permissions.

Anti-patternsWhere you should not use it

  • External orchestration of non-Databricks systems. Keep Airflow/Dagster on top.
  • Heavy fan-out (>1000 parallel tasks). Use Spark inside one task.
  • Sub-minute event-driven workflows. Use Structured Streaming or a Databricks App webhook.
  • Long-running interactive sessions. Tasks are batch side effects.
  • Storing significant state between tasks. TaskValues are tiny; pass UC table names.
  • Cron jobs that should be DBSQL alerts. Hourly threshold checks belong in Alerts.
  • Complex branching on data content. Embed in one notebook with Python control flow.
  • Cross-workspace orchestration. Jobs are workspace-scoped.
  • Job clusters as long-lived shared infra. They're ephemeral by design.
  • Business logic in TaskValues/params. Knobs, not config systems.

WeaknessesWhere it does not do well

  • DAG ergonomics past ~30 tasks. Use Asset Bundles + YAML.
  • No native rich conditional skipping. Embed in a notebook.
  • TaskValues are string-KV with low size. Not a workflow data system.
  • Cluster start dominates short tasks. A 10-second task can take 90s. Use pools or serverless.
  • Repair semantics surprise. Repair re-runs failed + downstream; can't isolate one task easily.
  • For-each result aggregation is awkward. Write to a UC table within the sub-task.
  • Permissions are coarse. No "edit only this branch" granularity.
  • Cross-task logs are not unified. No first-class cross-task tracing.
  • Limited backfill ergonomics. Re-run a parameterised date range via API; no UI affordance.
  • Cron timezone/DST confusion. Pin timezone explicitly.
  • No Airflow-style runtime dynamic task mapping. For-each list must be known at job start.
  • Cost attribution requires system tables. Build dashboards off system.billing.usage + system.workflow.*.
