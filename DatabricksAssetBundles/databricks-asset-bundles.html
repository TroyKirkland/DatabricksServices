L100What it is

IaC for Databricks workloads. Define jobs, pipelines, dashboards, apps, schemas — and 40+ resource types — as YAML (or Python), version in Git, deploy with databricks bundle deploy. Per-env overrides via targets.

  • YAML or Python manifest (databricks.yml or programmatic).
  • Targets: dev/staging/prod with overrides.
  • Resources: jobs, pipelines, dashboards, apps, models, schemas, model serving, vector search, clusters, Lakebase, Genie spaces, MCP services, secret scopes, and more.

L200The product surface

  • databricks.yml + includes (or Python programmatic definition).
  • Resources: jobs, pipelines, models, experiments, dashboards, apps, schemas, volumes, catalogs, external_locations, alerts, clusters, instance_pools, sql_warehouses, model_serving_endpoints, quality_monitors, vector_search_endpoints/indexes, genie_spaces, lakebase_*, mcp_services, secret_scopes.
  • Targets with workspace URL, run-as, variable values, overrides.
  • Typed variables (type: complex for structured values); prompts for interactive.
  • Modular file inclusion.
  • CLI: validate / deploy / run / destroy / sync / generate. Requires CLI v0.218.0+.
  • Workspace-only mode: no local CLI needed if artifacts live in workspace.
  • CI integrations (GitHub Actions, Azure DevOps, GitLab).

L300Architecture

[Project repo] → databricks bundle deploy → CLI validates, resolves, uploads, upserts → workspace reconciled
                          state in UC volume (.bundle/state) tracks prior deploys

Idempotent reconciliation. Run-as per resource per target.

L400Deep internals

Manifest + merging

  • Base + targets; later targets override earlier.
  • Variables ${var.foo}; built-ins ${bundle.target} etc.

Resource model

  • Each resource typed; same schema as REST API.
  • Cross-resource refs: ${resources.pipelines.X.id}.

Lifecycle

  • validate: parse + type-check; no remote calls.
  • sync: upload sources to workspace / UC volumes.
  • deploy: apply diffs via REST; preserve IDs by name.
  • run: trigger declared workload.
  • destroy: remove bundle-owned resources.
  • generate: reverse-engineer YAML from existing workspace resources.

State + ownership

  • State tracks bundle-managed resources.
  • Outside-bundle resources unaffected (unless name conflict).
  • Multiple bundles per workspace OK if no name collisions.

Per-target overrides

  • Cluster size / serverless / schedule.
  • Source paths.
  • Permissions (dev wide; prod restricted).

Variables + secrets

  • Variables typed; defaults; prompts.
  • Secrets via Secret Scopes {{secrets/scope/key}}.

Source artifacts

  • Notebooks, wheels, SQL files, exported dashboard JSON.

CI/CD pattern

  • PR: bundle validate.
  • Merge: deploy --target staging.
  • Manual gate to prod.
  • Rollback: redeploy prior commit.

Limits / realities

  • Some preview resources lag.
  • No first-class cross-bundle deps.
  • Rename = delete + create unless migration logic.
  • Big bundles slow deploys; modularise.
  • Notebook format gotcha (.py vs .ipynb).

Mental model

"Terraform for Databricks workloads." YAML (or Python) as source of truth; reconcile-style deploy.

Anti-patternsWhere you should not use DABs

  • Workspace creation itself. Use Terraform for that.
  • Single one-off jobs.
  • Runtime config. YAML is deploy-time.
  • Secrets in YAML. Use Secret Scopes.
  • One giant org-wide bundle. Modularise.
  • Cross-environment resource refs.
  • As a workflow language.
  • State as immutable.
  • Skipping validate in CI.
  • Auto-destroy of prod from CI failure path.

WeaknessesWhere it does not do well

  • Preview resource coverage gaps.
  • No cross-bundle imports.
  • Rename ergonomics rough.
  • Limited YAML templating.
  • No first-class plan/diff.
  • UI edits drift state.
  • Local dev slower than UI.
  • Notebook PR diffs ugly.
  • Secret vs literal confusion.
  • Permissions modelling verbose.
  • No unit-test framework for YAML logic.
  • CLI version pinning needed in CI.
