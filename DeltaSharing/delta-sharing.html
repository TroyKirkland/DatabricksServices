L100What it is

Delta Sharing is an open protocol for sharing live Delta data between organizations without copy. Provider exposes tables; recipient queries via REST returning short-lived pre-signed URLs to underlying Parquet files; reads happen directly on cloud storage.

  • Open protocol: public spec; any client.
  • Live data, no copy: recipient reads provider's actual files.
  • D2D vs D2O: Databricks-to-Databricks (UC-native) vs Databricks-to-Open (token-based).

L200The product surface

  • Share — UC securable bundling tables/views/volumes/notebooks/models/MVs.
  • Recipient — workspace (D2D) or generic token identity (D2O).
  • Recipient profile (D2O) — JSON with endpoint + bearer token; consumed by open delta-sharing client.
  • Grant — connects share to recipient.
  • Read: D2D = foreign catalog in UC; D2O = OSS library.
  • CDF: shareable; recipients read via table_changes.
  • Pushdown: partition filters and predicates limit URL signing.

L300Architecture

[Provider Databricks workspace]                                     [Recipient]
  UC managed tables                                                    │
  + Share definition                                                   │
        │                                                              │
        ▼                                                              ▼
  Delta Sharing server (control-plane REST API)  ◄────── auth + list/query ───────  D2D UC catalog
        │                                                              OR
        ▼                                                              D2O delta-sharing client
  Pre-signed URLs to Parquet files in provider's cloud storage  ◄── direct read ─── recipient compute

Thin REST control plane + bulk reads from cloud storage via pre-signed URLs. No engine on provider; recipient does compute. Pre-signed URLs expire (minutes/hours). D2D piggybacks on UC for permissions, lineage, audit. D2O uses bearer token + provider-side server logs.

L400Deep internals

Wire protocol

  • REST: /shares, /schemas, /tables, /query.
  • /query takes predicates, returns paginated file objects with pre-signed URLs.
  • URLs expire (~1h default); recipient re-signs.

D2D

  • Provider creates SHARE; grants to recipient (metastore ID + cloud + region).
  • Recipient: CREATE CATALOG ... USING SHARE → read-only UC catalog.
  • UC-managed perms, lineage, audit (system.access.outbound_*).
  • Cloud-native trust; no bearer token.

D2O

  • Token-based; provider emits recipient profile JSON.
  • OSS delta-sharing library reads.
  • Token rotation/expiry/audit is provider's job.

Pre-signed URL mechanics

  • S3 GET / Azure SAS / GCS signed URLs using provider credential.
  • Bearer-like; HTTPS only; treat as transient credentials.

CDF over sharing

  • table_changes() works across sharing when provider enabled CDF.
  • Feeds downstream LDP APPLY CHANGES INTO.

Filtering pushdown

  • Partition + predicate filters pushed to server; only matching files signed.
  • Liquid clustering prunes effectively via stats.

Provider-side controls

  • Token / IP allow-lists (D2O).
  • Read quotas; revocation via DROP RECIPIENT.
  • Audit in system.access.outbound_*.

Limits / realities

  • Pre-signed URLs in flight survive revocation until TTL.
  • Streaming tables / MVs shareable with caveats.
  • Views: Spark SQL only, no UDFs.
  • Notebooks / models D2D-only.
  • Egress accrues to provider.

Mental model

"Parquet over HTTPS, brokered by a tiny server." Recipient gets pre-signed URLs, reads direct. UC layers governance on D2D; D2O falls back to bearer tokens. No copy; queries hit live data.

Anti-patternsWhere you should not use Delta Sharing

  • Cross-region with egress sensitivity. Provider pays.
  • Real-time low-latency feeds. Seconds, not ms.
  • Sharing OLTP-like data. Version skew.
  • Recipient-specific row-level security. Use Clean Rooms.
  • Internal same-metastore sharing. UC grants suffice.
  • Non-Delta data. Wrong tool.
  • Forwarding pre-signed URLs around. They're credentials.
  • Always-on 24/7 streaming recipients. Egress + re-sign load.
  • Shared tables you VACUUM aggressively. Breaks recipient reads.
  • Distributing huge raw history. Share a sized snapshot instead.

WeaknessesWhere it does not do well

  • Egress accrues to provider.
  • Revocation isn't instant. URLs outlive grant.
  • CDF caveats. Schema changes can interrupt recipient.
  • D2O auditing thinner than D2D.
  • Views are limited. No UDFs / complex.
  • Notebooks/models D2D-only.
  • Bandwidth tuning is provider-side.
  • OPTIMIZE invalidates cached URLs.
  • No per-recipient dynamic filtering.
  • Recipient does compute. Slow on thin recipient cluster.
  • Marketplace inherits constraints.
  • Cross-cloud egress brutal.
